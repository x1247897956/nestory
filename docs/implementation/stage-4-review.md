## 质量结论

**暂不通过：两项 P2，其中一项可破坏任务层级并令恢复对象在列表不可见。**

### P2：恢复会绕过 Task 只有一层子任务的约束

位置：`internal/trash/trash.go:170`（Restore 写回之前）；相关既有校验 `internal/task/task.go:152`。

确定的服务调用路径：创建顶层 A、B 和 A 的子任务 C；删除 C；把 A 移为 B 的子任务；恢复 C 的删除批次。移动校验仅统计 `deleted_at IS NULL` 的孩子，因此删除 C 后允许移动 A。恢复只检查祖先是否被删除和项目是否归档，A、B 都存活，会直接恢复 C，产生 B → A → C 两层子任务。任务列表只展开顶层的一层孩子，恢复的 C 随之无法从正常任务列表访问。

建议：恢复事务应验证恢复后的 Task 层级，遇到父任务已变为子任务时返回明确冲突，要求先移回父对象；也可在移动时将相关软删除后代纳入限制。增加该调用序列的服务回归测试，保证拒绝时整批不产生部分恢复。此发现由完整代码路径确认，本轮未另跑用例。

### P2：delete-preview 缺少 spec 明确要求的后代清单

位置：`internal/trash/trash.go:17`、`:59`；`web/src/features/trash/DeleteButton.tsx` 确认对话框。

技术设计接口表明确规定 delete-preview 返回“当前版本、影响数量与后代清单”。当前 Preview 只有 version/count，SQL 也只 count；确认对话框只显示数量。因此删除多层 Page 或父 Task 时，用户无法在提交前核对具体哪些后代会被删除。回收站的批次成员是删除后的信息，不能补足删除前的预览契约。

建议：预览返回当前存活作用域的对象 id/title（适当显示层级/路径），确认框提供清单；保持根版本与数量的事务复核。若 Preview 增加 slice，不能再直接用结构体 `v != in`，应显式比较 version/count，成员由服务端重新计算。

## 验证范围说明

现有用例覆盖先删后代再删祖先的批次隔离、被删祖先阻止恢复、删除数量和根版本变化再次确认、关系保留占位、归档禁止恢复及跨日/DST 搜索分页等。它们没有覆盖“后代删除期间，存活父任务被降为子任务，再恢复后代”的组合。现有绿灯不消除上述两项发现。
