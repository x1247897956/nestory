# 搜索与集合读取性能修复

用户已授权直接解决实测两个瓶颈，普通实现细节自主处理。

目标：消除查询时反复解析完整块JSON；正式集合界面不传输正文；保留原有子串搜索、中文/特殊字符、排序/分页、归档/回收站恢复、版本和编辑恢复语义。

搜索选择SQLite内建FTS5 trigram及派生文本内容表，由数据库触发器与源对象在同一事务更新。表仅是可重建的搜索索引，块JSON仍是唯一编辑/导出正文；不提供写入派生文本API。不采用按词MATCH替换LIKE，避免改变短中文/符号含义。正常LIKE由trigram候选加速；短查询与需ESCAPE的字面符号查询在派生文本上匹配，不回到块JSON。匹配ID一次物化，再取得总数、排序和分页，避免双重正文扫描。实时连接原项目状态，删除/恢复更新索引，归档无需重建。

替代方案：单纯扩大SQLite缓存不能解决扫描增长和浏览器59MB载荷；外部搜索服务不适合单人部署；新存储正文格式会破坏块唯一来源。因此只增数据库派生索引与显式属性读取。

集合选择include_body=false参数（默认保持旧API完整对象），SQL不读取正文列，JSON不输出body_document。TypeScript将集合属性与完整详情类型区分；编辑器只接收详情GET/创建/更新返回的完整对象。列表、看板、日历拖动及父任务选项只使用属性，不用省略正文的对象覆盖详情缓存。

验收：真实SQLite迁移/触发器回滚与删除恢复；新旧搜索结果对照（标题/正文/表格/附件名、字面%_\\、中英大小写、短中文、空和超出页）；属性响应不含正文、默认完整响应和详情不变。重复同镜像数据规模测量并保留相同旧端点数据以便对比；实际界面参数另测响应体积。Docker升级前备份，副本迁移演练，最终恢复/持久化检查。搜索索引会增加磁盘和写入成本，必须测量保存延迟及索引规模。
