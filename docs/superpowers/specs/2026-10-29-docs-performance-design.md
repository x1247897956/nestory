# 文档同步与加载性能

## 目标与选择

用户要求完成文档统一和性能优化，并保留此前撤销摘要接口的决定。现行产品说明作为统一入口；历史设计与验收原文只加历史标识，不改写过去的测试事实。README和架构中与当前实现直接矛盾的笔记层级UI、编辑模式、自定义属性/筛选描述改为当前行为。

基线在独立容器中通过真实API建立每类1000个对象、约8KB重复文本的块正文：浏览器笔记页额外请求约8.4MB任务数据，主入口包含原生块编辑器约1.74MB JavaScript。

相比重新设计列表摘要/分页协议，本轮选择不改变对象结构：编辑器由React.lazy按需加载并提供加载失败恢复；任务查询只在任务页/项目汇总（含汇总来源详情背景）启用；GET JSON用Go标准库gzip BestSpeed协商压缩。写接口、静态文件、附件、Range和已有Content-Encoding透传；Host/Origin保护保持在压缩前执行。缓存使用Vary区分Accept-Encoding。没有Redis、缓存业务对象、数据库迁移或依赖升级。

## 验证与边界

先用旧镜像验证无关请求回归、为压缩新增测试；对比首屏脚本字节、解码数据量和压缩前后字节一致性，记录实际样本下的准备时间与内存，不以单次时间作稳定承诺。编辑器下载失败应显示恢复入口且不写坏正文。完整端到端覆盖导航、详情、自动保存、附件、归档与恢复；容器升级前后备份核对。

压缩只降低网络传输，不减少JSON解码后的对象内存；完整列表仍读取正文、没有无限规模保证。分页/虚拟列表等需要进一步依据使用规模测量，不在本轮悄悄改变筛选、父子上下文或返回协议。
